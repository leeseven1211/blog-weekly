小七的周刊（第 032 期）：当 AI 开始动手，观测就不能缺席 ​

这里记录每周值得分享的科技内容，每周一发布（北京时间 07:00）。

本期 3 个要点 ​

  1. 会行动的系统，首先要会留下证据：日志、链路和操作记录决定了自动化出错后能否复盘。
  2. 浏览器自动化正在变成基础能力：真正的门槛不是点按钮，而是权限、状态和失败处理。
  3. 供应链的安全感来自可验证来源：签名、锁文件和构建记录要成为发布流程的一部分。

封面图 ​

封面图：金门大桥。跨越并不只靠跨度，也靠持续检测和维护；自动化系统同样需要能看见自己的运行状态。

本周短谈 ​

1. 速度越快，越需要一条时间线 ​

AI agent 从“给建议”走向“执行任务”后，最容易被低估的不是模型能力，而是过程可见性。一次调用涉及提示、工具、权限、外部响应和最终写入，任何一环出错都可能只留下一个模糊的失败结果。把 trace id 贯穿请求，把关键决策和工具参数记录下来，再为敏感动作保留人工确认，排查才不会退化成猜测。小团队未必需要昂贵平台，但至少要能回答：谁在什么时候，以什么输入，调用了什么动作。

2. 自动化不是把人从流程里删除 ​

最成熟的自动化系统往往不是“全自动”，而是把人的注意力放到少数高价值判断上。部署机器人可以自动跑检查，但生产变更仍应有清楚的边界；客服 agent 可以整理上下文，但退款和身份变更应有可撤销路径。真正值得测量的指标也不只是成功率，还包括误操作恢复时间、人工接管比例和不可逆动作数量。对低风险、重复性任务可以放大权限，对高风险任务则宁愿慢一点。

3. 来源链条会成为产品体验的一部分 ​

软件依赖、模型权重和数据集都像一条供应链：最终用户看到的是成品，但风险可能藏在上游。锁定版本只是起点，构建系统还要记录来源、生成时间和校验结果。对个人项目，先从 lockfile、依赖审计和发布清单开始；对团队，则把 provenance 作为构建产物一起保存。它不能保证没有漏洞，却能让“出了问题找不到谁改的”变成可解决的问题。

科技与 AI 动态 ​

1. OpenTelemetry 把观测数据推向统一语义 ​

【事实】OpenTelemetry 持续推进 traces、metrics 和 logs 的统一采集与传输规范，已经成为跨语言、跨厂商观测的共同接口。它解决的是“数据怎么离开应用并被统一理解”，不是替你自动解释业务故障。

【推测】随着 agent 调用链变长，统一上下文会比单一平台的漂亮仪表盘更重要。落地时先为一条关键用户路径补齐 trace，再决定要不要扩大采集范围；过早全量采集，成本和噪声都可能失控。

2. Playwright 继续降低浏览器测试与自动化门槛 ​

【事实】Playwright 提供跨浏览器自动化、追踪记录和并行测试能力，常被用于端到端测试，也被用于需要浏览器交互的工作流。它让“能操作网页”更容易，但登录态、验证码和外部页面变化仍然是工程问题。

【推测】浏览器 agent 的竞争会从点击准确率转向失败后是否能解释和恢复。开发者可以先把它限制在测试环境，保存 trace 和截图，并为每个外部动作设置超时与撤销策略。

3. Sigstore 让无密钥签名更接近日常发布 ​

【事实】Sigstore 通过短期身份、透明日志和无密钥签名，降低了开源项目验证制品来源的门槛。签名能回答“谁的工作流生成了它”，不能回答“代码本身是否没有漏洞”。

【推测】未来的软件安装体验会更自然地包含来源证明。团队不必一次性重做所有流水线，可以先给发布制品签名，再逐步把构建环境、依赖清单和验证动作纳入门禁。

世界之最 ​

1. 世界最长的天然拱桥：贵州织金洞天生桥 ​

贵州织金洞的天然桥，石灰岩地貌形成的自然结构。

它的“最长”不是一根桥梁的单项纪录，而是多个工程系统协同的结果。复杂软件也一样，单个服务很快不代表整体可靠，接口和观测才是连接处的质量。

2. 世界最大的室内主题公园：阿布扎比法拉利世界 ​

阿布扎比法拉利世界，巨型室内空间中的主题设施。

高度带来风、温度和维护等额外变量。系统规模扩大后，指标不能只看峰值性能，还要关注故障传播和恢复路径。

3. 世界最大的盐湖：里海 ​

从卫星视角看里海，世界面积最大的内陆水体。

观测能力越强，越需要过滤噪声和校准设备。日志系统也是如此：不是记录越多越好，而是要让关键异常从噪声中被看见。

4. 世界最大的单体钟：明永乐大钟 ​

北京大钟寺博物馆收藏的明永乐大钟。

单体巨物一旦成形，日常维护和状态监测就成了长期成本。自动化流程同样不能只在成功时表现良好，异常路径更值得测试。

5. 世界最大的沙漠：南极冰盖 ​

南极冰盖，按降水量衡量它其实属于荒漠。

大工程的可靠性来自持续监测、分层控制和预案，而不是建成那一刻的规模。软件平台上线后，也要把维护预算和故障演练算进总成本。

工具深挖 ​

1. OpenTelemetry Collector：把数据送到该去的地方 ​

Collector 可以在应用和后端之间承担接收、处理、采样与转发，减少业务代码直接绑定某家观测服务。它适合已经有多种语言和多个后端的团队；小项目若只有一个服务，直接使用 SDK 可能更简单。小七判断：先解决数据边界，再追求平台统一。

2. Grafana：把时间线变成可读的现场 ​

Grafana 擅长把指标、日志和告警放进同一观察面。它不能替团队定义什么是重要信号，所以仪表盘应围绕用户路径和服务等级目标设计，而不是把所有曲线都贴上去。适合已有数据源的团队，不适合拿来掩盖埋点缺失。

3. Trivy：给容器和依赖做快速体检 ​

Trivy 可以扫描容器镜像、文件系统和依赖中的漏洞与配置问题，适合作为 CI 的第一道反馈。扫描结果不等于风险排序，团队仍需结合是否可达、是否在生产启用和是否有修复版本来判断。先把高危结果接入发布流程，别一开始就让全部告警阻塞开发。

4. OpenSSF Scorecard：检查开源依赖的维护信号 ​

Scorecard 会检查分支保护、依赖更新和工作流权限等信号，适合引入第三方依赖前做初筛。它不是安全证明，也不该取代代码审查，但能把“这个项目看起来可靠吗”变成可重复的起点。

本周冷知识 / 彩蛋 ​

  • 🥚 冷知识：可观测性里的 trace 原本就有“追踪”之意，它不是一张报表，而是一条跨服务的事件时间线。
  • 🧠 彩蛋：机场黑匣子并不是真的黑色，重点也不是“永远不坏”，而是事故后仍能提供证据。日志保留策略同理。

小七的碎碎念 ​

这周看到“全自动”三个字时，我的第一反应已经不是兴奋，而是去找回滚按钮。系统会做事当然重要，但它能不能把过程讲清楚，往往才决定人类敢不敢把下一步交给它。

意外推荐（非科技） ​

《切尔诺贝利的祭祷》（纪实文学）

切尔诺贝利核事故纪念雕塑，提醒人们事故记录也是公共记忆。

这本书不提供工程教程，却让人看到事故如何穿过数据、制度和个人生活。对技术工作者来说，它提醒我们：指标背后总有人承担后果，设计系统时要把“谁会被影响”写进风险模型。
